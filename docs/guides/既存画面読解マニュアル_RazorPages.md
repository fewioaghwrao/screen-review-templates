# 既存画面読解マニュアル_RazorPages

## 1. 目的

本資料は、**既存Web画面を改修する前に、どこをどう読めばよいか** を整理したマニュアルです。  
Razor Pages の画面を題材にしていますが、考え方自体は **既存ASP.NET系画面や他の既存Web画面の読解** にも応用できるようにまとめています。

本マニュアルの目的は、以下のとおりです。

- 既存画面の構造を把握しやすくする
- 画面修正時に、どのファイルを確認すべきか迷いにくくする
- 共通部品と画面固有部品を切り分けやすくする
- UI改修前に影響範囲を整理しやすくする
- 読解結果を詳細設計書、確認観点、テスト資料へつなげやすくする

---

## 2. 対象

本資料では、主に以下のような画面改修を想定しています。

- CSS差し替え
- 色・フォント・余白の調整
- ラベルや説明文の見直し
- 入力欄・ボタン・一覧表示の見え方改善
- 共通部品の影響確認
- 軽微な画面挙動改善
- 画面設計書修正や確認観点整理の前提調査

また、本資料は主に **UI改修を中心とした既存画面読解** を対象としており、  
大規模な業務仕様変更や全面的な再設計を前提とするものではありません。

---

## 3. このマニュアルで扱う読解の考え方

既存画面の読解とは、単に `.cshtml` を見ることではありません。  
画面を安全に修正するには、少なくとも以下をつないで読む必要があります。

- 画面本体
- PageModel
- 共通レイアウト
- 部分共通化された部品
- CSS
- 表示条件
- JavaScript
- submit / 遷移先
- 共通スタイルか画面専用スタイルか
- 他画面への影響有無

つまり本資料でいう「読解」とは、

**「その画面が、どのファイルで・どの条件で・どの見た目と挙動で成立しているかを把握し、どこを触ると何に影響するか判断できる状態にすること」**

を指します。

---

## 4. 読解の基本手順

既存画面を読むときは、次の順で進めると整理しやすくなります。

### 4.1 画面の目的を先に確認する
最初に、その画面が何のための画面かを把握します。

確認例:
- 何を表示する画面か
- 誰が使う画面か
- 主操作は何か
- 一覧画面か、入力画面か、確認画面か
- 画面遷移上どこに位置するか

この段階では、細かい実装より **業務上の役割** を掴むことを優先します。

---

### 4.2 対象画面の本体ファイルを見つける
次に、対象画面の `.cshtml` を確認します。

Razor Pages では、画面本体に以下のような要素がまとまっていることが多いです。

- 見出し
- 説明文
- 入力欄
- ボタン
- テーブル
- メッセージ領域
- モーダル起動要素
- `class` / `id`
- `asp-page` や `asp-route-*`
- 条件分岐やループ

この時点では、**見た目の入口** を掴むことが目的です。

---

### 4.3 PageModel を確認する
`.cshtml.cs` を確認し、画面の裏側で何をしているかを見ます。

確認例:
- 初期表示時に何を取得しているか
- 画面に渡している Model は何か
- 検索条件や表示件数をどこで受けているか
- submit 時にどの処理が呼ばれるか
- メッセージ表示に使う値はどこで設定しているか
- 状態変更やCSV出力などの処理入口はどこか

ここでの目的は、**見た目だけの問題か、処理も関係するかを切り分けること** です。

---

### 4.4 共通レイアウトを確認する
画面崩れや余白、ヘッダ・フッタ・全体幅の問題は、画面本体ではなく共通レイアウト側で決まっていることがあります。

確認対象例:
- `_Layout.cshtml`
- 共通ヘッダ
- 共通フッタ
- ナビゲーション
- 共通コンテナ
- 共通のCSS / JS読込

ここでは、**画面固有ではなく全画面共通の責務がどこにあるか** を掴みます。

---

### 4.5 CSS の効き先を確認する
既存画面改修では、ここが特に重要です。

確認するもの:
- 共通CSS
- 画面専用CSS
- ライブラリCSS
- class / id の定義元
- 読込順
- 上書き関係
- 詳細度（specificity）

確認したいこと:
- この見た目はどのCSSで決まっているか
- 共通スタイルか画面専用スタイルか
- 他画面でも同じclassを使っていないか
- 上書きで済むか、HTML構造の見直しが必要か

---

### 4.6 表示条件・分岐を確認する
見た目の崩れや表示漏れは、条件分岐が原因のことがあります。

確認例:
- `if`
- `foreach`
- 権限による表示切替
- データ有無による出し分け
- 状態に応じたボタン活性 / 非活性
- エラー時だけ出るメッセージ

ここでは、**通常表示だけでなく条件付き表示も含めて読む** ことが大切です。

---

### 4.7 JavaScript の有無を確認する
UI修正でも、表示切替やモーダル、送信中表示などは JavaScript が関わることがあります。

確認例:
- パスワード表示切替
- 送信中表示
- モーダル開閉
- ローディング表示
- 再読込処理
- ボタン活性 / 非活性制御
- CSVダイアログ表示

CSSだけで済むのか、スクリプトも見る必要があるのかをここで判断します。

---

### 4.8 submit / 遷移先を確認する
ボタンやリンクは、見た目だけでなく遷移や処理の入口になっていることがあります。

確認例:
- `form method="post"`
- `asp-page`
- `asp-action`
- `asp-route-*`
- `OnPost`
- `OnGet`
- 詳細画面リンク
- 削除や更新の submit 先

ここでは、**見た目修正だけで影響が閉じるのか、処理側にも関係するのか** を見極めます。

---

### 4.9 共通部品か画面固有部品かを確認する
改修の影響範囲を判断するうえで必須です。

確認したいこと:
- ボタンスタイルは共通か
- 入力欄スタイルは共通か
- テーブルやカードの見た目は共通か
- メッセージ表示領域は共通か
- この class を変えると他画面にも効くか

ここで共通 / 個別を切り分けると、詳細設計や確認観点が書きやすくなります。

---

### 4.10 影響範囲をまとめる
最後に、読解結果を影響範囲として整理します。

整理例:
- 直接影響する要素
- 間接影響しそうな共通部品
- 他画面確認が必要な箇所
- 対象外に切れる箇所
- 見た目だけの修正か、補助処理も含むか

---

## 6. 画面改修で特に確認したいポイント

### 6.1 「見た目」と「仕様」を混同しない
見た目を直したいだけなのに、実は業務仕様を変えてしまうと危険です。

例:
- ボタン文言を変える → UI変更
- ボタン押下条件を変える → 仕様変更
- エラーメッセージ位置を変える → UI変更
- バリデーション条件を変える → 仕様変更

まずは、どこまでが見た目で、どこからが仕様かを切り分けます。

---

### 6.2 共通CSSを直接触る前に利用箇所を確認する
共通CSSの変更は影響が広いため、安易に触らない方が安全です。

確認例:
- 他画面で同じ class を使っていないか
- 画面専用CSSで吸収できないか
- 既存の共通スタイルと役割が重複していないか

---

### 6.3 表示条件付き要素を見落とさない
通常表示だけ見て修正すると、エラー時や件数ゼロ時に崩れることがあります。

確認例:
- エラーメッセージ表示時
- 入力エラー時
- データ0件時
- 権限制御時
- Done 状態など更新不可状態

---

### 6.4 小画面表示も読む
レスポンシブ対応がある場合、PCだけ見ていると不十分です。

確認例:
- テーブルがカードへ切り替わるか
- ボタンが折返すか
- 長い文言がはみ出さないか
- モーダルが小画面でも使えるか

※ 小画面表示の確認は、CSS・共通レイアウト・必要に応じてJavaScriptの観点で確認します。

---

### 6.5 修正対象外を意識して読む
読解時点で「何を変えないか」を切っておくと、その後の設計が安定します。

例:
- 認証処理は対象外
- DBアクセス処理は対象外
- 状態遷移ルール自体は対象外
- ページング仕様は対象外

## 8. 詳細設計書につなげる考え方

既存画面の読解結果は、そのまま詳細設計書の材料になります。

たとえば、読解で次が分かれば、

- どの要素があるか
- どこが共通か
- どこが個別か
- 何が対象外か
- どこに影響しそうか

詳細設計書では、次に落としやすくなります。

- 改修概要
- 対象画面
- 修正対象要素
- 変更内容一覧
- 項目別詳細
- 実装方針
- 共通部品・影響範囲
- 対象外
- 確認観点

つまり、

**読解は詳細設計書の前工程**

として扱うと整理しやすいです。

## 10. Razor Pages を題材にした読解例

### 10.1 ログイン画面での読解例
確認したいこと:
- タイトルや説明文はどこで描画されているか
- 入力欄の class は何か
- エラーメッセージはどこで表示されるか
- パスワード表示切替は CSS か JS か
- 送信中表示はどこで切り替えるか
- 認証処理そのものはどこまで対象外に切れるか

### 10.2 案件一覧画面での読解例
確認したいこと:
- 検索入力欄と件数切替の見た目はどこで決まるか
- 検索ボタンとクリアボタンの差別化はどこで行うか
- 一覧行の区切りや補足情報はどの class が効いているか
- ページャは画面本体か共通部品か
- 一覧データ件数が変わったときの表示崩れはないか

### 10.3 タスク一覧画面での読解例
確認したいこと:
- サマリー表示の件数はどこで集計しているか
- 状態バッジや優先度バッジの表示はどこで決めているか
- 状態変更の disabled 制御はどこで行っているか
- CSV出力は画面だけの導線か、処理も含むか
- モバイル表示は CSS 切替か構造分岐か
- 小画面時の確認は、CSS・共通レイアウト・必要に応じてJavaScriptの観点で見ているか

---

## 11. 注意点

- Razor Pages はあくまで題材であり、旧ASP.NET Web Forms や MVC5 と完全に同一ではありません
- ただし、**既存画面を読んで影響範囲を把握し、改修前提を整理する考え方** は十分共通しています
- 実案件では、さらに以下も必要になる場合があります
  - マスターページや古い共通部品の読解
  - 複数CSSの競合確認
  - JavaScript / jQuery 主導画面の追跡
  - サーバーサイド表示制御の読解
  - レガシー構成特有の命名や分割ルールへの対応

---

## 12. まとめ

既存画面改修では、いきなり修正に入るのではなく、まず **既存画面の読解** を行うことが重要です。

本資料で整理した読解の流れは、次のようにつながります。

**既存画面を読む**  
→ **共通部品と画面固有を切り分ける**  
→ **影響範囲を整理する**  
→ **詳細設計書へ落とす**  
→ **確認観点を整理する**  
→ **テスト・本番移行資料へつなげる**

Razor Pages はその練習台として扱いやすく、既存画面改修の考え方を整理する題材として有効です。  
本マニュアルは、画面修正前の調査・読解・整理の入口資料として活用することを想定しています。
